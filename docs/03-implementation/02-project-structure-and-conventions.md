# 02 — Project Structure and Conventions

Three codebases, one set of habits. The goal is that a teammate can guess where a file lives before
searching for it, and that a reviewer can see the architecture from the folder tree alone.

## 1. Firmware conventions (`firmware/`)

```
firmware/
├── platformio.ini
├── include/
│   ├── sr_config.h              # pin map, intervals, topic templates, plausibility ranges
│   ├── build_info.h             # FW_VERSION, git hash (generated by a PlatformIO extra_script)
│   └── secrets.example.h        # shape of secrets for local dev; secrets.h is git-ignored
├── lib/
│   ├── ringbuffer/              # fixed-size sample buffer in NVS (unit-testable on host)
│   └── filters/                 # median + EMA implementations (pure, no Arduino deps)
├── src/
│   ├── main.cpp                 # setup(): init peripherals, start tasks; loop(): watchdog feed + status
│   ├── sensors/
│   │   ├── sensor_base.h        # `interface ISensor { bool begin(); optional<Reading> read(); }`
│   │   ├── sht31_sensor.cpp/.h
│   │   ├── bh1750_sensor.cpp/.h
│   │   ├── ltr390_sensor.cpp/.h
│   │   └── ds18b20_sensor.cpp/.h
│   ├── sampling/sampler.cpp      # SamplerTask: read → filter → stamp → enqueue to ring buffer
│   ├── net/
│   │   ├── wifi_manager.cpp     # provisioning portal, reconnect with backoff
│   │   ├── mqtt_transport.cpp   # TLS connect, publish, LWT, subscribe to cmd, ack
│   │   └── http_fallback.cpp    # HTTPS POST when MQTT is unreachable for > 5 min
│   ├── storage/config_store.cpp # NVS: secret, intervals, offsets, seq counter
│   ├── ui/oled.cpp              # claim code, live values, fault icons
│   └── diag/logger.cpp          # serial logging with a compile-time level
└── test/
    ├── test_filters/            # native (host) tests via `pio test -e native`
    └── test_ringbuffer/
```

Rules:
- **No business rules in the firmware.** No thresholds, no severity, no alert decisions — it reports
  values, faults and health only (architecture rule 4).
- **No `delay()` in tasks.** Use `vTaskDelay`; the sampler task runs at 1 Hz and sleeps.
- **Every sensor behind `ISensor`**, so a fake implementation can run the whole pipeline on the bench
  (`07-appendices/04` §6 "bench mode").
- **Naming:** `snake_case` files, `PascalCase` types, `camelCase` members, `kConstantName` constants.
- **Secrets never in source.** `secrets.h` is git-ignored; the firmware ships with *no* device secret —
  it receives one at claim time.

## 2. Backend conventions (`backend/`)

### 2.1 Layer responsibilities

| Project | May contain | Must not contain |
|---|---|---|
| `Domain` | Entities, enums, value objects, domain rules (`ThresholdBand.Validate()`, `Alert.Escalate()`) | EF Core, HTTP, MQTT, `ILogger` |
| `Application` | Use-case services (commands/queries), DTOs, validator classes, interfaces (`IMqttPublisher`, `INotificationChannel`, `IDeviceSecretHasher`, `IClock`) | `DbContext` usage in callers, HTTP types, MQTTnet types |
| `Infrastructure` | EF Core `DbContext`, configurations, migrations, repositories, MQTT client/broker host, FCM/Telegram/SMTP clients, PBKDF2 hasher | Business decisions (it implements interfaces, it does not decide) |
| `Api` | Endpoints/controllers, request/response models, auth policies, SignalR hub, background workers, DI wiring, `Program.cs` | Direct SQL, domain logic beyond mapping |

### 2.3 Naming and style

- C# conventions (PascalCase public members, `_camelCase` private fields, `Async` suffix for awaitables).
- One public type per file; file name = type name.
- Endpoints grouped in `MapXxxEndpoints()` extension methods, not a 400-line `Program.cs`.
- **Nullable enabled, warnings as errors**; `dotnet format` must be clean (NFR-07).
- Result pattern for expected failures (`Result<T>` with a problem code), exceptions only for bugs:
  a rule like "target min must be below target max" is a `Result`, a null reference is an exception.
- Every validator has a name that appears in the RFC 7807 `code` field, e.g. `threshold_ordering_invalid`.
- XML docs on every public class and non-obvious method — the rubric asks for commented code, and
  comments must explain *why* (band ordering, dwell, hysteresis) rather than restate the code.

### 2.4 "How to add a metric" (a 6-step checklist, used as a review template)

1. Add a row to the `Metric` seed (code, unit, precision, plausibility range, `IsCore`).
2. Extend the firmware `ISensor` set + `sr_config.h` plausibility range (if physical).
3. Extend the MQTT payload mapping in `IngestWorker` (short keys in `samples[]`).
4. Add a default threshold to each built-in `SpeciesProfile` seed **with a source reference**.
5. Add the metric to the dashboard card list + chart metric selector (client is data-driven from the
   `Metric` dictionary, so usually zero code changes).
6. Add unit tests for plausibility + band resolution, and one widget/UI test for the card.

If any step requires editing more than one file per layer, the design has regressed.

## 3. Flutter app conventions (`app/`)

```
app/lib/
├── main.dart
├── app.dart                        # MaterialApp.router, themes, localisation delegates
├── core/
│   ├── env.dart                    # API base URL per flavour
│   ├── formatting.dart             # metric formatting, duration, relative time
│   ├── result.dart                 # Result<T> + AppFailure (maps API problem codes to messages)
│   └── status.dart                 # MetricStatus enum + colour/icon mapping (single source of truth)
├── data/
│   ├── api_client.dart             # http + auth header + problem+json parsing + retry policy
│   ├── auth_api.dart, terrarium_api.dart, device_api.dart,
│   │   reading_api.dart, threshold_api.dart, alert_api.dart, summary_api.dart
│   ├── live_client.dart            # SignalR connection, reconnect, group subscribe
│   └── local_cache.dart            # last-known values + pending mutations (non-secret)
├── models/                         # immutable DTOs with fromJson/toJson + `copyWith`
├── state/
│   ├── auth_provider.dart          # session, tokens (secure storage), current user
│   ├── terrarium_provider.dart     # list, selection, CRUD
│   ├── telemetry_provider.dart     # latest values per terrarium, live subscription, staleness
│   ├── alert_provider.dart         # inbox, filters, ack/resolve, badge count
│   ├── threshold_provider.dart     # effective thresholds + overrides
│   ├── device_provider.dart        # fleet, claim flow, config commands
│   └── settings_provider.dart      # language, theme, notification prefs
├── screens/                        # one folder per screen S4…S16 from 02-design/04
├── widgets/
│   ├── metric_card.dart, status_badge.dart, band_label.dart, staleness_chip.dart,
│   ├── alert_tile.dart, range_selector.dart, chart_panel.dart, coverage_badge.dart
└── l10n/app_{vi,en}.arb
```

Rules:
- **`provider` only** (rubric mentions Provider/Bloc; Provider is chosen — ADR-011 alternative note).
  `ChangeNotifier` + `Selector`/`Consumer`; no `setState` for shared data, only for local widget state
  (animation, text controllers).
- **Screens do not call APIs.** Screens read providers; providers call `data/` clients. Enforced by review
  and by the fact that `api_client.dart` is not imported under `screens/`.
- **One status→colour mapping** in `core/status.dart`. A second place that decides red/green is a bug.
- **Never render a value without its timestamp.** `MetricCard` requires a `capturedAt` argument — the
  compiler enforces the UX rule from `02-design/04` §6.
- **All user-facing strings via `AppLocalizations`**; a test greps for hard-coded literals.
- Naming: files `snake_case.dart`, classes `PascalCase`, providers `XxxProvider`, private widgets
  prefixed `_`.

## 4. Web dashboard conventions (`web/`)

- Vanilla ES modules; **no build step** — a demo must not depend on `npm install` succeeding.
- `js/api.js` is the only place that knows the API base URL and attaches the bearer token
  (token kept in memory + `sessionStorage`, never `localStorage`, because it is a shared demo machine).
- `js/i18n.js` mirrors the ARB keys; `TC-I-15` compares key sets so translations cannot drift.
- One file per page in `js/pages/`; `wallboard.html` has no navigation chrome.
- Chart.js instance per chart, disposed on page unload; no chart re-creates on every push (only
  `chart.data` is appended, capped at 720 points client-side).

## 5. Cross-cutting conventions

| Topic | Convention |
|---|---|
| Branching | `main` (demo-ready) · `feat/*` · `fix/*`; PRs require green CI and one review |
| Commit messages | `area: imperative summary` (`api: reject implausible humidity values`, `fw: fix SHT31 CRC retry`) |
| Versions | SemVer per component: firmware `1.2.0`, API `1.2.0`, app `1.2.0+12`. The app shows firmware version in the fleet view (FR-16) |
| Comments | Explain *why* and cite the requirement (`// BR-11.4: hysteresis prevents flap on the band edge`). Never comment out code — delete it |
| Error handling | Expected → `Result` + problem code; unexpected → exception → 500 + correlation id; both are logged |
| Logging | Structured with `CorrelationId` for ingest batches; never log secrets, tokens or full payload dumps |
| Time | `DateTimeOffset` in code, `datetime2(3)` in DB, UTC at rest, convert only at the UI edge |
| Tests | Mirror the source tree: `ThresholdEvaluatorTests.cs` ↔ `ThresholdEvaluator.cs`; test names read as sentences (`GivenValueAboveTargetForFourMinutes_ThenNoAlertIsRaised`) |
| Formatting | `dotnet format`, `dart format`, `clang-format` (via PlatformIO) — all three run in CI |

## 6. Documentation duties

- Any change to a requirement, threshold default or API shape updates the matching file in this doc set
  **in the same PR**. The traceability matrix (`04-quality/04`) is the checklist that keeps this honest.
- Every ADR-worthy decision made during implementation is appended to `07-appendices/01-adr-log.md`
  (append-only, one paragraph: context, decision, consequence).
